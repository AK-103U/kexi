# 首次初始化移出请求生命周期并由闹钟驱动

首次数据库初始化（Database Initialization）在 Durable Object 闹钟（Alarm）中执行，前台请求和定时任务不进入内容管理系统（CMS），在就绪前返回 503 状态。

首次初始化包含 90 条核心数据库迁移与默认内容模型种子（Seed），在 Cloudflare D1 边缘数据库上需要数百次网络往返，耗时通常达一至两分钟，超过平台在短请求结束后提供的约 30 秒后台执行窗口（`waitUntil`）。访客断开连接或爬虫提前中止，会导致未完成的迁移被打断，留下无法自动释放的数据库迁移锁；并发访问还会导致相互等待和锁超时。

本方案在保持自动资源创建与绑定的前提下解决此生命周期冲突：

1. **执行与请求解耦**：引入轻量持久化协调器 `KexiInitializer`（基于 SQLite 的 Durable Object）。首个请求只在协调器的持久化事务中登记初始化任务并激活闹钟，不直接执行任何数据库写入。
2. **稳定的执行窗口与重试机制**：闹钟拥有最长 15 分钟的执行时间，不受客户端生命周期影响；部署更新或实例重置时，平台自动在全新实例中重新执行该闹钟，恢复未完成的工作。
3. **安全的所有权与锁恢复**：任务启动前先在协调器中持久化唯一的所有权标记（Token）。迁移适配器在申请 D1 锁时携带该标记，遇到打断重试时仅认准自己已持久化的所有权，绝不凭时间戳盲目抢占外部 CLI、其他实例或管理员正在进行的迁移。
4. **统一的状态反馈**：前台请求与每分钟定时任务在初始化完成前均被拦截，公开页面返回带有自动刷新和 `Retry-After: 3` 的友好提示页，API 请求返回规范的 503 结构；就绪后所有请求透明放行，进入管理员注册向导。

这一选择增加了轻量 Durable Object 的绑定，换取了真正零手动运维、零 CLI 迁移的纯自动 Fork 部署体验，彻底消除了由请求取消打断引发的数据库迁移死锁。
